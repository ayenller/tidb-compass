30 秒开场话术

TiDB 是面向现代应用的分布式 SQL 数据库，兼顾事务处理与实时分析能力， 能在保留 SQL/MySQL 生态习惯的同时，提供弹性扩展、高可用与更低的架构复杂度。

Distributed SQL HTAP MySQL Compatible Cloud Native

省 减少分库分表、中间件、同步链路与多套系统叠加。

模块 3

典型客户场景怎么讲

这一块建议作为“客户代入区”，让销售或伙伴按行业现场切换案例话术。

互联网平台 / 电商

高峰期并发上升、实时推荐和运营分析需求并存，适合重点讲扩展性、HTAP 和架构简化。

金融核心周边 / 交易类系统

关注连续性和数据一致性时，建议把 TiDB 放在“关键业务的现代化升级”叙事中。

出海业务 / 多地域业务

适合介绍多地域部署、业务连续性和统一数据平台价值，避免客户把问题拆成多套本地数据库。

实时经营分析

  • 客户不想再等待夜间 ETL 或长链路同步。
  • 希望交易数据更快转化成运营动作。
  • 需要一套更适合“边跑业务边看分析”的平台。

模块 4

竞品对比建议用“架构路径”而不是只列厂商 Logo

这样更适合伙伴和售前在不同客户现场复用，也更方便后续根据市场变化更新内容。

对比维度 TiDB 单机/主从 MySQL 分库分表 + 中间件
扩展方式 面向水平扩展设计 容易遇到单机瓶颈 可扩，但治理复杂
开发习惯 保留 SQL / MySQL 生态习惯 原生熟悉 跨库逻辑与路由复杂
交易 + 实时分析 更适合统一平台叙事 通常需要额外分析链路 链路更多，实时性与运维更复杂
高可用设计 分布式架构更利于故障隔离 依赖主备切换与单点治理 组件多，故障面更广
长期运维复杂度 平台化空间更大 前期简单，后期容易补丁式演进 团队成本与系统复杂度持续上升

对比模块的设计原则

  • 避免绝对化措辞，多讲“更适合解决什么问题”。
  • 优先对比架构路径，再按行业补充具体厂商。
  • 给销售留出“补一张行业竞品表”的扩展位置。
  • 把重点放在客户当前痛点，而不是只堆产品 feature。

模块 5

常见客户疑问与页面预埋回答

这部分适合做成可折叠 FAQ，帮助销售和伙伴统一答法。

迁移成本会不会很高？

建议从应用兼容性、SQL/MySQL 生态习惯、演进式迁移路径去回答，而不是承诺“零改造”。

核心业务真的能放上来吗？

建议用“关键业务稳定性要求高、需要高可用与持续服务能力”的框架回答，并结合 PoC 设计落地。

为什么不继续用 MySQL 加分析库？

把讨论引导到链路延迟、系统数量、治理复杂度与实时运营需求是否值得长期承受上。

客户现有架构已经能跑，为什么还要换？

适合从业务增长、未来改造成本、平台化能力和团队效率角度展开，而不是只谈技术先进性。
